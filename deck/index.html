The Problem

Banks want to modernize. They're afraid to.

80%+ of transactions

Run on IBM i / IBM Z, much of it in COBOL batch that has run untouched for decades.

Senior COBOL developers are retiring

The pattern is a knowledge cliff — the people who understand the business rules are leaving.

Modernization risk is the blocker

"Tests pass" on generated code means nothing until you've shown the new output matches the old.

The question every bank asks first is not "did you generate code?" — it's "is it the same?"

Why this wins

Many teams work with Bob. Few prove the output is correct.

The first thing any bank wants is a guarantee the rewrite is behaviorally identical. We built the mechanism that delivers it.

What we built

ParityProof pipeline

  • COBOL reference runtime — GnuCOBOL Docker image runs the original batch on flat-file inputs.
  • Business-rule catalog — Bob explains each program; Karthik sanity-checks the rules.
  • Java 21 modernized program — Spring Boot CLI job; copybook becomes a fixed-width record class.
  • Edge-case input generator — zero/negative balances, half-cent rounding, max field sizes, leap dates, empty files.
  • Parity runner — runs both on every input, diffs every field by the copybook layout → results.json.
  • CI + dashboard — GitHub Actions fails the build unless parity is 100%; Azure-hosted live dashboard.
Every output keeps the original fixed-width format so the diff is exact.
Live proof

Parity catches real bugs

Interest batch, acct 1: COBOL 00000043208 (432.08). Java with HALF_DOWN rounding: 00000043207 (432.07).

CORRECTHALF_UP → 100% pass, 20/20 fields
INJECTED BUGHALF_DOWN → 90% FAIL, INTEREST + NEW-BAL flagged

One preview: speed of verification — a full COBOL + Java compile-and-parity run completes in seconds in CI, so every Bob edit is checked on the spot via a hook. Usability and performance measured by the runner, not a guess.
