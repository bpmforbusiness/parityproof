The Problem

Banks want to modernize. They're afraid to.

80%+ of transactions

Run on IBM i / IBM Z, much of it in COBOL batch that has run untouched for decades.

Senior COBOL developers are retiring

The pattern is a knowledge cliff — the people who understand the business rules are leaving.

Modernization risk is the blocker

"Tests pass" on generated code means nothing until you've shown the new output matches the old.

The question every bank asks first is not "did you generate code?" — it's "is it the same?"

Why this wins

Many teams work with Bob. Few prove the output is correct.

The first thing any bank wants is a guarantee the rewrite is behaviorally identical. We built the mechanism that delivers it.

Most teams

What we built

ParityProof pipeline

  • COBOL reference runtime — GnuCOBOL (verified 3.2.0) runs two original batch programs: ACCOUNT-INT and TXN-POST (signed amounts, COMP-3). A Dockerfile exists but is not yet built.
  • Business-rule catalog — drafted with Bob and Claude Code, line citations verified; Karthik's business review is pending.
  • Java 21 twins — plain single-file programs; BigDecimal arithmetic; copybook layout → fixed-width output.
  • Edge-case input generators — half-cent rounding, zero and tiny balances, negative balances, sign handling, and field-limit overflow (silent COBOL truncation, reproduced).
  • Parity runner — diffs every field of every record, per program, by the copybook layout → result.json; exits non-zero on any mismatch.
  • Gate + dashboard — run.sh fails unless parity is 100%; a GitHub Actions workflow is written (not yet run on GitHub); a static dashboard is built (hosting planned).
Every output keeps the original fixed-width format so the diff is exact.
Live proof

Parity catches real bugs

Interest batch, acct 1: COBOL 00000043208 (432.08). Java with rounding changed to DOWN (injected): 00000043207 (432.07).

CORRECTHALF_UP → 100% pass, 64/64 fields
INJECTED BUGDOWN → ACCOUNT-INT 20/24 FAIL, INTEREST + NEW-BAL flagged (a deliberate mutation, not a Bob change)

Every run is saved under evidence/runs/<timestamp>/ (inputs, both outputs, result.json): a real PASS and a real injected FAIL are committed, and the runner also fails cleanly when a COBOL or Java output is missing.

Key learning

Parity-as-a-test-harness changes how a migration is trusted: it turns an article of faith ("Bob's code works") into a measurable, verifiable guarantee — which is exactly the evidence a bank asks for before signing off. It also surfaced hidden COBOL behavior (silent overflow truncation) that a naive rewrite would have "fixed" and broken parity.
